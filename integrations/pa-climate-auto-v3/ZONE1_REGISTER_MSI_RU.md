# Zone 1 — зарегистрировать сейчас, DS18B20 подключить завтра

## Подтверждено физически

- Контроллер Zone 1 уже прошит по USB объединённым образом `pa-climate-msi-2.0.1`.
- Реальный MAC, прочитанный esptool: `20:9B:A9:8C:D2:58`, device ID `PA-CLIM-209BA98CD258`.
- Стартовый UART: `WiFi=OFF, cloud=NOT_CONFIGURED, devices=0, T1=FAULT, T2=FAULT, relay=OFF`. Это ожидаемо без USB provisioning и без датчиков.
- Подключение обоих DS18B20 к GPIO27 владелец выполняет завтра. **Не ждать датчиков для регистрации.** При отсутствии обоих датчиков физический нагрев должен оставаться OFF.
- Zone 2 `PA-CLIM-209BA98CD370` продолжает работать. Её регистрация и ключи не меняются.
- Сайт `/monitoring/pa/climate`, карточки и дизайн **не менять**.

## Задание локальному Codex на домашнем MSI — выполнить

1. Получить изменения ветки `work/pa-climate-auto-msi-20261110` в `simscope/Farmplast`, пакет `integrations/pa-climate-auto-v3`.
2. На **реальном работающем MSI** найти **существующее** размещение Climate module в подключённом HTTP gateway. Не создавать новую службу, порт, базу, таблицу, Docker. Сохранить резервную копию двух существующих файлов модуля перед точечной заменой:
   - `integration/fetch-existing-runtime.mjs`: по действующему уже авторизованному маршруту `/climate/workstation/devices` разрешить **только** `device_id=PA-CLIM-209BA98CD258`, `zone_id=pa-zone-1`, `migration_confirm=MIGRATE EXISTING PA ZONE 1`. Остальные защищённые зоны и старый ID Zone1 остаются запрещёнными.
   - `server/storage.mjs`: новая Zone1 регистрируется в режиме **OFF**, так что завтрашнее подключение датчиков не запустит отопление без команды владельца.
3. Обновить **только** эти файлы в фактическом рабочем модуле MSI. Перезагрузить/перечитать **существующий** gateway способом, используемым им сейчас, без другого порта, новой службы или сброса данных. **Не заменять `climate-state.json`, `workstations.json`, OTA-релизы, DPAPI-файлы, ключи и другие проекты.**
4. Проверить, что существующие Zone 2 и токен рабочей станции остаются действующими. **Не вызывать заранее локальный `POST /v1/admin/devices` для Zone 1**: он создаст одноразовый секрет, который потом не сможет получить уже готовый Windows-скрипт. Регистрация должна быть атомарной **на рабочем Windows через авторизованный workstation API**, чтобы сразу сохранить приватные ключи в DPAPI.
5. Подтвердить, что `POST /climate/workstation/devices` с указанным ID, Zone 1 и `migration_confirm` теперь **разрешён**, не отправляя запрос регистрации заранее. Проверить это на программных тестах, не расходуя реальный одноразовый ключ.
6. Уведомить владельца одним сообщением: `MSI ZONE1 MIGRATION ROUTE READY`. **Не сообщать `REGISTERED`**, пока Windows-скрипт не сообщит `USB PROVISION PASS`, а сервер не увидит устройство.
7. На Windows-компьютере с подключённой Zone 1, без повторной прошивки, запустить скрипт:
   `automation/Provision-Zone1-Already-Flashed.ps1` через PowerShell, `-Port COM4`. Скрипт автоматически проверит MAC, создаст единственную запись `pa-zone-1` и сохранит уникальный ключ в DPAPI, а затем передаст конфигурацию устройству по COM4.
8. После `FP_PROVISION_OK` удостовериться, что `pa-zone-1` ONLINE, `sensor_count=0`, `heat=false`, `desired.mode=OFF`; `pa-zone-2` не изменилась. Не требовать двух датчиков сегодня. Не запускать отопление.

## Проверки и запреты

Тесты `node --test server/tests/fetch-runtime.test.mjs` должны подтверждать: запрет произвольных MAC и зон, точное разрешение известного физического MAC Zone1, однократность без вращения секрета, режим OFF, 0 датчиков с нормальной телеметрией, Zone2 без изменения.

**Никаких новых таблиц, отключения защищённых маршрутов, отключения PIN, повторной прошивки ESP32, перемены GPIO16 или редизайна.** Если MSI не может применить код, честно сообщить причину; не выдавать изменение GitHub за регистрацию в работающем MSI.
