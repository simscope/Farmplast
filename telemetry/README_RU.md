# Farmplast NJ → MSI: состояние подготовки

Работа продолжается: MSI получает реальные пакеты всех трёх чиллеров в режиме mirror. Прямой адрес в прошивках ещё не переключён. Бочки остаются на прежнем источнике до USB-установки.
Пользователь сейчас не имеет физического доступа к контроллеру двух бочек.
Старые строки телеметрии разрешено удалить только после проверки нового потока всех пяти устройств.

## Подготовлено

- Приёмник `server.mjs`: только текущие значения в RAM, никаких записей в БД, файлы или журнал запросов. На диске находятся только код, справочник точек и отдельные ключи доступа.
- Фиксированные устройства и точки, отдельные ключи четырёх производителей данных (два уровня бочек отправляет один контроллер), отдельный ключ чтения, ограничение размера и частоты запросов.
- Истечение показаний: CH1 — 16 секунд, CH2/CH3 — 45 секунд, бочки — 35 секунд. Просроченные значения удаляются из памяти. Перезапуск начинается с пустого состояния.
- Сохранены масштабы Modbus и существующая перестановка бочек на сайте: экранная бочка 1 ← BARREL-NJ-02; экранная бочка 2 ← BARREL-NJ-01.
- Чтение для сайта через защищённый серверный API Vercel, с проверкой пользователя Supabase Auth и отдельным списком UUID. Все ответы `no-store`. Кадровые и расчётные API не меняются.
- Подготовлен `VITE_NJ_TELEMETRY_SOURCE=msi` с серверным списком `NJ_TELEMETRY_MSI_ASSETS=CH-NJ-01,CH-NJ-02,CH-NJ-03`. API объединяет чиллеры MSI с двумя бочками прежнего источника. Недоступность бочек не скрывает работающие чиллеры.
- Изолированная установка MSI: `E:\SimScopeData\Farmplast\NJTelemetry`, loopback `127.0.0.1:18220`, задача `Farmplast-NJ-Telemetry` от Local Service при загрузке Windows, без входа пользователя.
- HTTPS `https://msi.tail4626fb.ts.net:10000/healthz` отвечает 200 с проверкой сертификата; неавторизованное чтение — 401. Все три чиллера уже передают реальные пакеты в RAM через проверочный mirror. Порты Hvac и AI Manager сохранены.
- `prepare-barrels.py` подготовил отдельный приватный исходник на MSI: `private\barrels-candidate\Barel2`. Адрес, bearer и проверка TLS заменены; исходные Modbus, калибровки и экран сохранены. Исходник не скомпилирован и не установлен; реальная установленная версия пока не подтверждена. Ключи и Wi-Fi находятся только в приватном `secrets.h` на MSI.

## Что препятствует завершению

Адрес Supabase встроен в прошивки. Бочки не имеют OTA; нужно USB-подключение Waveshare ESP32-S3-Touch-LCD-7. Исходник на MSI: `D:\Farmplast\Tank-Barrel1\Barel2\Barel2.ino`; его соответствие реально установленной версии ещё нужно подтвердить перед прошивкой.

Найдены исходники и приватные конфигурации именно установленных версий `ch1-edgefree-2`, `ch2-edgefree-1`, `ch3-edgefree-1`. SHA исходных бинарных файлов совпадают с одобренными релизами, отпечатки ключей совпадают с сервером. Отдельные производные исходники находятся в `firmware/msi`, реальные заголовки и сборки — вне Git.

Проверен и установлен OTA/control adapter. MSI валидирует пакет и хранит показания в RAM; в облако отправляются только метаданные обновления и временные параметры подтверждения команд CH1. Они не записываются в таблицы показаний. Сохраняются только ограниченные служебные OTA receipts и результаты команд. Подписанный ответ возвращается устройству без изменения. Проверки покрывают новую загрузку, подтверждение по фактическому состоянию, повторяемый reset, неверные ключи и отсутствие записей измерений.

Миграция `20261117002722_farmplast_nj_msi_telemetry_bridge.sql` применена с начальными маршрутами `cloud`, после чего включён проверочный `mirror`. Режим `relay` отключает старый writer и передаёт пакет синхронно в RAM MSI без очереди в БД. Это промежуточный транспорт и путь совместимости для отката старой прошивки. Новые прошивки `ch1-msi-1`, `ch2-msi-1`, `ch3-msi-1` используют HTTPS 443 `/api/nj-ingest/chiller-N` сайта Farmplast → MSI; Supabase из пути передачи показаний исключён. До установки нельзя считать этот прямой путь проверенным на устройствах.

Ни одна прошивка не отправлялась на устройства; выходы, уставки и режимы оборудования не менялись.

## Оставшиеся шаги

1. Подтвердить исходники и секретные локальные конфигурации реально установленных прошивок. Подготовить и скомпилировать бинарные образы отдельно под каждую плату. Не использовать старые D: исходники чиллеров как подтверждённую производственную версию.
2. Опубликовать проверенный сайт, переключить чиллеры по одному из mirror в relay и проверить реальные ответы, затем установить прямые MSI-прошивки штатным механизмом OTA. Адаптер уже установлен; до завершения нужны проверка прямого транспорта и подтверждённые новые загрузки.
3. Подключить контроллер бочек по USB и установить проверенную прошивку с новым защищённым адресом MSI. Сохранить текущие пины, Modbus, калибровки и экран. Проверить оба уровня и их физическое соответствие.
4. Переключать чиллеры по одному с наблюдением реального оборудования и возможностью восстановления. Для CH1 учитывать, что перезагрузка затрагивает контроллер выходов.
5. В Vercel настроить серверные `NJ_TELEMETRY_UPSTREAM`, `NJ_TELEMETRY_READ_KEY`, `NJ_TELEMETRY_ALLOWED_USER_IDS`. Ключ чтения никогда не получает префикс VITE_. Публичный адрес приёмника уже подготовлен: `https://msi.tail4626fb.ts.net:10000`. Серверная проверка HTTPS выполнена через Tailscale клиента; отдельная проверка с контроллера через заводскую сеть ещё предстоит.
6. Убедиться, что MSI получает все пять потоков, время и значения обновляются; отключение источника даёт OFFLINE и очищает значения, перезапуск не восстанавливает историю. Только затем включить источник `msi` на сайте и проверить все пять страниц.
7. Остановить старые пути записи телеметрии и удалить разрешённые старые строки из `telemetry_latest`, `telemetry_latest_import`, `ch2_latest`, `ch3_latest`, `asset_points_latest` после повторной проверки зависимостей. Не удалять справочники, Auth, кадровые, расчётные и управляющие данные и весь проект Farmplast. Отдельной таблицы `telemetry_history` в текущем публичном каталоге нет.

Настройка автозапуска не равна испытанию физической перезагрузкой MSI. До фактической проверки это ограничение остаётся.

## Проверки подготовки

Новые проверки покрывают путь настоящего PostgREST SDK → защищённый web API → HTTP-приёмник RAM, проекции с номерами компрессоров, фильтры RAW, нулевой уровень, независимую потерю одного датчика бочек, изоляцию ключей, атомарный отказ неверного пакета, предел объёма текущего состояния и точные сроки истечения. Для этих тестов использованы синтетические значения; они не отправлялись в работающий сервис MSI и не являются проверкой реальных датчиков.

Сборка клиента и ESLint изменённых JS/JSX проходят. Общий ESLint содержит 44 исходных ошибки в уже собранном `public/pa-climate/serial-loader.js` и 6 предупреждений вне изменений. Общий набор тестов первоначально дал 222/233; два теста SSR прошли после задания синтетических VITE-переменных. Оставшиеся ZKT-тесты останавливает защитная проверка неизменного compatibility baseline; она воспроизводится в отдельном worktree исходного коммита `f657a91`. Эти кадровые SQL и проверки не изменялись. Нельзя считать весь проект полностью зелёным или перенос принятым на основании этих проверок.
